## 修复行为

| 问题 | 修改 | 验证结果 |
| --- | --- | --- |
| F1：UA 覆盖或关闭原生透传后，gzip 解码成明文却保留 `cch=00000` | 将原字节保留、CCH 重算和 TLS profile 选择分开。未变更的已验证 gzip 可原样保留；已知版本需要明文时重算 CCH；未知格式需要不安全转换时返回 400 | 556 组转发的逻辑正文及发送字节全部相等；16 个实际发送用例中，8 个原始 gzip 完全一致，8 个明文匹配独立原生 CCH oracle；PCAP 匹配、零丢包 |
| F2：错误转换丢失 `cf-ray`，原生 CLI 把来源拒绝误判成中间代理拒绝 | 保留 `cf-ray` 的存在性及原值，包括空值和不同大小写键；复制头值切片，避免别名修改 | 持续 403、仅带 cf-ray 时，原始和转换后的响应均只发 1 次请求；request-id 对照同为 1 次，无标记对照仍为 3 次 |
| F3：非标准 JSON / 纯文本解析错误失去 gzip 降级信号 | 按固定版本的 8192 字节探测、JSON schema 优先级及文本规则识别错误，映射为安全、短小的标准解析错误；防止 trim、嵌套提取或错误 schema 意外制造重试信号 | 两种非标准格式、标准格式及转义扩展用例，在 cf-ray / request-id 下，原始与转换后响应都经历 gzip → gzip → 明文，共 3 次请求后成功 |

F3 还覆盖了 JSON 转义扩展：原消息或 error.type 中大量 `<` 在重新编码后会膨胀，可能超过 CLI 的探测上限。识别成功后固定输出短消息及 `invalid_request_error`，确保完整响应仍可被探测，不回显解析器片段。回归也覆盖 BOM、ECMAScript 尾部空白、重复键、大数、超长 JSON、错误 schema、嵌套消息及正反重试分类。

账户身份、会话绑定和默认隔离保护保持有效。108 个策略用例中，既有 OAuth 身份冲突仍在本地拒绝。关闭原生透传不能绕过未知 CCH 的正文变更保护。

## 原生回放与真实接口测试

断网 Docker 中，22 个错误场景产生 58 条模型请求，其中 40 条 gzip；接收记录与解密 PCAP 全部相等，内核丢包为 0。SDK 普通重试固定为 0，因此这里观察的是原生压缩降级控制器。

生产恢复服务与原生 CLI 联调覆盖 3 个模型 × 2 种认证 × 2 条独立对话，包含连续压缩、迁移和续聊：96 条生成、24 条计数，未发现跨会话串入。存储和上游成功响应为本地测试实现，不代表真实订阅或官方服务验收。

维护者另行授权了真实中转地址及凭据。客户端在 Docker internal 网络中运行，唯一出口为仅允许该域名的 CONNECT 代理，不挂载宿主登录配置。新凭据的模型列表请求使用 Bearer 返回 200，单独 x-api-key 返回 401；消息接口两种认证都返回 200。原生 2.1.292 CLI 成功结束，生产 Forward 导出的 normal / passthrough 请求也通过生产 HTTPUpstream 实际发送并返回 200，总计 5 个短生成用例成功。原先地址的模型列表被 403 拒绝，未进行生成。

这些真实请求验证中转接口可用性和组件发送链路，不验证官方 CCH、订阅、风控或完整部署。生产 Forward 与 HTTPUpstream 的真实测试为两阶段组件联调。原始凭据、响应标识及账号信息不纳入仓库；测试代理、网络和临时凭据文件已清理。
