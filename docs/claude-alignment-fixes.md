## 压缩历史的验证

同一客户端 session 和同一上游 session 可以连续压缩；压缩本身不会切换账号或创建新的上游 ID。

1. 原生摘要请求必须覆盖本会话已记录历史的合法前缀。支持摘要指令独立成消息，或合并进末尾用户消息。
2. 已闭合的工具调用关系必须保持。不能把外来助手消息、未知工具结果或其他会话的 thinking 放进摘要输入。
3. 完整摘要响应经过固定 CLI 版本的展示规范化后，加密保存在本会话材料中。客户端传来的压缩标记不能替代这份证据。
4. 下一轮的新前缀必须包含本会话实际生成的摘要；保留的最近回复及 5.5 system 控制帧必须匹配原记录。
5. 成功完成新历史的首轮请求后，在同一个数据库事务中替换历史、清除旧检查点、取消旧摘要工作器租约，
   并按需清除当前段的旧恢复前缀。旧工作器不能回写覆盖新状态，账号永久归属不变。
6. 失败或明确拒绝不消耗待接受的摘要；结果不确定时停止自动重放。替换成功后不能再次用同一摘要授权历史回退。

### 自定义 API 地址

实时 CLI → 生产服务实验进一步发现：自定义 base URL 会省略请求分类和压缩头。
因此分类头不是唯一入口。固定 2.1.292 CLI 的完整摘要指令形态可以触发同样的前缀校验，
但摘要响应、被覆盖历史和保留回复仍必须逐项验证。

同时保存真实摘要请求 / 响应的普通续聊分支：用户恰好引用同一段摘要指令、却没有压缩本地历史时，
正常续传也不会被误拒绝。两种分支都来自网关实际观察到的输入和响应，不接受任意改写。

这不是任意 `/resume`、历史编辑、分叉或远程协作协议的放行开关。未捕获的截断格式、无法匹配的
保留消息、跨模型 / 协议历史依然会明确停止。普通无损 resume 的原有行为保留。

## 隔离与持久性

客户端对话仍按认证用户、分组和 session UUID 隔离。待确认的摘要记录位于已有 AES-GCM 历史密文中，
继续绑定本会话与数据用途，无需新增数据库表或迁移。

会话压缩不会改变永久账号绑定。之后在已支持的普通用户回合发生托管迁移时，创建新的上游 UUID，
恢复正文仍先对相同账号和 session 计数。新历史不能套用压缩前的旧恢复前缀。

5.5 的消息级 output_config、tools、clear_at 也纳入历史哈希，不能更改控制语义后仍冒充同一条历史。
普通扩展 metadata 仅来自当前请求，没有账号级缓存或跨 session 复用。
