## 1. 交互 CLI 与 print 模式必须分开

本轮同时运行未修改二进制的真实 PTY 交互入口和 `-p` 入口：

| 特征 | PTY 交互入口 | `-p` 入口 |
|---|---|---|
| User-Agent 尾部 / billing entrypoint | `cli` | `sdk-cli` |
| 无自定义 system 的身份块 | 官方 CLI 身份句 | Agent SDK 身份句 |
| `--system-prompt` | 本轮未覆盖交互式替换选项 | 原文留在 system；身份块与原文块均观察到 1h 缓存 |
| `--append-system-prompt` | 本轮未覆盖交互式追加选项 | 保留默认提示词结构，并使用另一条 SDK 身份句 |

2.1.295 的提取模块 `chunk-14b6z3qz.js` 中 entrypoint 选择函数，与实测的
`print→sdk-cli / interactive→cli` 一致。两版源码中的固定包装标记与确认语精确字符串
均未找到；本轮官方运行也没有自动生成这些包装。字符串检索本身不能证明所有动态分支。

现有 sub2api 生成的 `cli` UA 可以对应交互入口，因此不能单凭它与 `-p` 不同就认定错误。
但也不能把 `-p` 样本的缓存 / 身份分支与交互入口的 UA 拼起来宣称整体相同。

PTY 场景使用独立测试 HOME、预写 onboarding / 目录信任状态、关闭内置工具、明确的配置源
与假 OAuth 环境令牌。它不是实际执行订阅登录，也不代表全部默认用户设置；界面显示的
账户类型不能用于确认订阅。模型回复后由采集器主动终止，退出 143 明确记作受控停止，
不冒充自然退出成功。额外观察到辅助会话命名请求，单列为产品流程，不据此要求 API 模式
制造无业务需要的请求。

## 2. 新模式给计数请求添加了未经对照支持的内容

将 CLI `/context` 发出的 36 个 count_tokens 请求正文，原样作为普通 API 计数输入：

- 旧模式：36 / 36 个出站 JSON 内容保持相同。
- 006 保留模式：36 / 36 个 system 改变；原先缺 system 的请求也被补入 billing / 身份块。

这些计数输入包含 CLI 为估算组成部分构造的探针，不能把每条探针当作完整生成请求。
新增 `ForwardCountTokens → rewriteClaudeOAuthSystem` 调用引入了这项差异。
006 的内部一致性测试证明“网关按所写策略注入”，不能证明该策略符合 CLI。

**优先修复：** 计数路径遵守调用方给出的计数正文，避免无条件补入生成前缀；若产品需要
估算完整转换后请求，另行明确接口语义与去重规则。当前假服务始终返回固定计数，本轮只
证明输入发生改变，没有测出真实多算多少 token。此问题仅在默认关闭的新模式启用时出现。

## 3. 固定三块 / 两块结构都不等于默认 CLI

两版 PTY 主请求均为四个 system 块：归因、身份、默认主提示词、另一组指令。
两个较长块分别带 `ttl=1h, scope=global` 与 `ttl=1h`。在本轮关闭内置工具的场景里，
两版主提示词长度分别为 10,598 / 10,617 字符，另一组为 16,043 / 16,020 字符。

旧模式用固定 1,541 字符扩充块、5m 缓存，再把调用方 system 搬进确认对话；
新模式保留原文但省去默认扩充与这些缓存布局。两者均没有还原上述结构。
`gateway_service.go` 中“2.1.x 一致”的通用扩充注释不能作为全版本依据：新抓包中
2.1.292 / 2.1.295 的默认开头和内容已不同。

**后续方向：** 按版本、交互 / print、替换 / 追加 system 和工具状态分别定义合同，
用来源证据决定哪些内容属于该模式。完整官方提示词包含操作环境与工具语义，不能只为
外观一致就无条件拷贝进任意第三方 API 对话。此前 006 保留原文的收益仍成立，但不能
升级为“已与 CLI 完全一致”的结论。

## 4. MCP 工具名与 Chat strict 的差异

官方 CLI 连接了本地无副作用的测试 MCP 服务，实际注册并发出六个工具，名称为
`mcp__alignment__...`。不是通过 EXTRA_BODY 覆盖工具字段得到的样本。

- 旧模式的两版本 × 三入口共六条请求中，36 个名称全部被改成动态别名，并添加工具缓存断点。
- 新模式相同六条请求保留全部 36 个原名。
- Chat 路径的两版本 × 两模式共四条请求中，24 个工具都额外出现 `strict:false`；输入没有
  strict，原生样本也没有。Messages / Responses 对应输入没有出现这项补值差异。

后者来自 `chatcompletions_to_responses.go` 的 `defaultStrictFalse`，再经
`responses_to_anthropic_request.go` 把中间协议值保留到 Anthropic 出站。
**修复应针对 Anthropic 目标区分省略与显式 false**，保留显式参数的语义；不能全局删除
真正 OpenAI Responses 路径可能需要的默认策略。此处证明字段差异，不声称服务端据此拒绝。

## 5. 条件字段、配置与比较边界

本轮 CLI 生成请求包含 `cache-diagnosis-2026-04-07` 和 diagnostics，普通转换没有生成
对应状态；这是一项能力 / 状态差异，应一起评估，不能只补 beta 头。
需要客户端真实状态的字段，不应用固定值伪造。

以下差异没有当作实现缺陷计入：独立请求的随机 ID、测试账号身份替换、实验设置
`API_TIMEOUT_MS=5000` 与网关缺省 600 秒、普通 Messages 输入未显式请求流式。
中间请求对象缺 Accept-Encoding 的差异，经真实传输检查已经由传输层补齐；不能只看
构建器对象就说线上发出的头不同。实际 HTTPS 服务端记录与 PCAP分别保留。

配置专项复验了未知版本 / 架构、自定义 origin、关闭原生传输、显式绑定 TLS profile 等
选择边界。当前通过声明只适用于命中已验证 profile 的配置；它不是线上部署核验结果。
