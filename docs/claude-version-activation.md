# Claude 版本发现与已验证配置选择

## 修复的问题

原后台会记录官方最新稳定版本，运行时直接使用这个值；普通 API→OAuth 转换却只允许
已验证的 2.1.292 / 2.1.295。没有手动覆盖时，发现一个更新但未验证的版本，就可能让
转换请求进入 `unsupported Claude compatibility version` 错误路径。

现在将发现与启用分开：

- `claude_code_client_version_synced` 继续保存发现的最高稳定版本，沿用每小时发现、
  草稿 / 预发布过滤、失败保留和不回退的既有逻辑。
- 自动选择只使用“不高于发现版本”的最高已验证配置。没有匹配项时，使用原来的
  环境变量 / 内置回退值。发现记录不会被改写成运行版本，也不需要数据库迁移。
- 手动固定值仍优先。合法但未验证的手动 / 环境值保留原行为，由转换守卫明确拒绝；
  不会偷偷换成另一个版本。非法语法沿用归一化与回退规则。

| 手动值 | 发现值 | 选择结果 |
|---|---|---|
| 空 | 2.1.295 | 2.1.295 |
| 空 | 2.1.300（模拟新版本） | 2.1.295 |
| 空 | 2.1.294 | 2.1.292 |
| 空 | 2.1.280 / 无有效发现 | 环境变量或内置值；默认 2.1.292 |
| 2.1.292 | 2.1.300 | 保持 2.1.292 |
| 2.1.300 | 任意 | 保留显式配置；API→OAuth 转换拒绝发送 |

已存在数据库里的未来版本发现值，在新进程读取时也会受到筛选，不必等下一次同步。
关闭自动同步只停止后续发现，保留原发现值并继续使用上述选择规则。手动 / 环境覆盖的
原有优先级不变。

## 单一准入表与检查

`internal/pkg/claude/verified_profiles.go` 是自动选择和转换守卫共用的准入表，限定为
已有完整默认 Linux x64 构造 / 传输验证的版本。返回给调用方的是副本，不能在运行时
添加未经验证的项。

增加一个版本仍需源码、固定二进制、Docker / 传输证据、变更记录，以及对应版本的头、
正文、CCH 和传输实现。`TestVerifiedCLIRegistryHasCompleteGatewayProfiles` 会对每个
登记版本执行生产构建，检查一致的 UA / 归因 / CCH 和非默认的原生传输配置；只添加
版本号而没有传输配置不能通过。这个测试不能代替官方样本与完整验收。

本轮不改变 2.1.292 / 2.1.295 的报文模板、模型能力或 TLS 行为，不下载新 CLI，
也不将任意 GitHub release 自动认定为已验证。已验证旧版本是否继续被真实服务接受，
仍需提供方观察；若最低版本发生变化，应验证并发布新配置。

## 管理页

新增两个只读响应字段，不接受界面回写：

- `claude_code_client_version_effective`：当前设置选出的基础版本。
- `claude_code_client_version_verified`：该基础版本是否在准入表中。

页面分别展示“最新发现版本”和“当前基础版本”，并提示未验证的显式配置。旧后端没有
这些字段时，不展示猜测的状态。它们描述基础配置，不包含模型级版本提升，也不等于
每个账号的自定义 origin / TLS 覆写都已经命中原生传输。
